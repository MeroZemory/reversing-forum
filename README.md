# Reversing All

리버스 엔지니어링의 질문, 분석 과정과 AI 활용법을 함께 나누는 커뮤니티입니다.
카톡은 대화의 중심으로 두고, 웹에는 정리하고 검증해 다시 쓸 수 있는 정보를 쌓습니다.

## 지금 만드는 것

큰 틀은 **자유 커뮤니티 → 정리·검증한 지식 → AI 보조**입니다.
첫 구현은 비회원의 글 읽기와 회원의 가입·글 작성·댓글을 연결합니다.
등록한 글은 비공개로 저장하고 Jev 최소검수를 통과하면 공개합니다.
보류되거나 API 오류가 발생한 글은 작성자만 볼 수 있습니다.
새 글의 기여를 기존 공개 글 전체와 비교해 의미 중복과 짜깁기를 확인합니다. 새 조건·근거·정정은 허용하고, 확인된 연관 글은 본문 아래에서 연결합니다.
최신 글과 자료 길잡이는 같은 글·댓글을 사용합니다. 자료 길잡이는 운영자가 현재 공개본을 확인하고 선택한 자료를 묶습니다.

위키, 상세 팩트체크, 회원이 호출하는 AI 댓글, 운영 도구는 [TODO.md](TODO.md)의 순서대로 추가합니다.
강의·실습·CTF는 후속 단계입니다. 세부 정책은 실제 흐름을 구현하며 필요할 때 결정합니다.

## 실행

Node.js 22.13 이상을 사용합니다.

```sh
npm install
```

`.env.example`을 `.env`로 복사하고 `BETTER_AUTH_SECRET`을 임의의 긴 값으로 설정합니다.
다음 명령으로 값을 생성할 수 있습니다. 생성한 값은 `.env`에만 보관합니다.

```sh
node -e "console.log(require('node:crypto').randomBytes(48).toString('base64'))"
npm run db:init
npm run dev
```

기본 주소는 `http://127.0.0.1:3000`입니다. `BETTER_AUTH_URL`도 같은 주소를 사용합니다.
현재 작업 환경에는 무작위 세션 비밀값을 가진 로컬 `.env`를 준비했습니다.

Jev 인증은 `TYPESAFE_API_KEY` 또는 `TYPESAFE_KEY_FILE`로 설정합니다.
키 파일의 기본 예시는 `C:/_authentication/typesafe-jev-api-key.txt`입니다.
키가 없거나 API가 실패하면 글은 공개되지 않습니다. 비밀값을 저장소에 넣지 않습니다.

회원가입에는 이메일 인증이 필요하며, 인증 메일 재전송·비밀번호 복구·Google 로그인과 가입·사이트 닉네임 설정을 지원합니다. 메일은 Resend 설정이 필요하고 Google 버튼은 공급자 설정이 있을 때 표시합니다. 인증·메일 설정은 `.env` 또는 `AUTH_CONFIG_FILE`에 둡니다.
이미 인증된 같은 이메일은 계정으로 연결합니다. 다른 Google 이메일의 연결은 계정 화면에서 직접 요청하고 최근 로그인을 확인합니다. Google로만 가입한 회원도 비밀번호를 설정하면 기존 이메일로 로그인할 수 있습니다. Google 연결을 해제하려면 인증된 이메일·비밀번호 로그인 수단이 남아 있어야 합니다.
Google 콜백은 `BETTER_AUTH_URL`의 origin에 `/api/auth/callback/google`을 붙인 정확한 주소를 등록합니다. 로컬 개발은 포트별 주소를 등록하고, 터널은 고정된 공개 주소를 사용합니다. 로그인 시작과 콜백은 같은 사이트 주소로 접근해야 합니다.

중복 후보 검색에는 로컬 CPU에서 고정된 비양자화 임베딩 모델을 사용합니다. 애매한 판정에는 예산이 설정된 격리 Codex CLI를 호출합니다. 설정 누락·오류·불확실한 결과는 공개를 보류합니다. 모델 파일은 로컬 캐시에 준비해야 하며 자료 배치의 비공개 예산 설정을 코드에 넣지 않습니다.

임시 운영은 Windows의 Node 서버·SQLite와 Cloudflare Tunnel을 연결하는 방식으로 준비했습니다. 현재 상태·병렬 작업 DAG·검증·합의 기록은 [중간보고서](docs/progress.html)에서 관리하고, 구현 선택과 실패·수정의 교훈은 [개발기](docs/development.html)에서 설명합니다.

신고 접수 목록은 이메일 인증을 마친 지정 운영자만 읽을 수 있습니다. 게시 편집 계정과 별도로 신고를 검토할 실제 계정은 `REPORT_REVIEWER_USER_ID`에 정확한 사용자 ID를 설정합니다. 이 설정은 신고 조회 권한만 부여합니다.

Windows에서 `powershell.exe -NoProfile -File scripts/install-production-startup.ps1`을 실행하면 현재 사용자의 로그인 후 숨김 실행을 등록합니다. 이미 실행 중인 감독 프로세스가 있으면 그대로 유지합니다. 이 연결의 실행 시점은 [Windows의 로그인 후 실행 규칙](https://learn.microsoft.com/en-us/windows/win32/setupapi/run-and-runonce-registry-keys)을 따르며, 로그온 전 부팅과 실제 재부팅 검증은 별도입니다.

## 폴더

```text
src/
  app/          페이지와 HTTP 진입점
  components/   데이터·이벤트를 받아 그리는 화면과 공통 UI
  features/     클라이언트 동작과 화면을 연결하는 진입점
  client/       API·인증 어댑터, 초안 저장과 동작 훅
  contracts/    서버와 화면 사이의 명시적인 데이터 계약
  server/       인증, 저장, 커뮤니티 동작, Jev 연동
  lib/          공통 타입과 표시 도구
scripts/        DB 초기화와 검증 도구
tests/          서버 테스트와 브라우저 테스트
legacy/         이전 구현을 원형 그대로 보존한 참고 자료
```

별도 API 서버나 여러 서비스로 나누지 않고 단일 Next.js 앱으로 시작합니다.
회원 세션은 [Better Auth](https://better-auth.com/docs/integrations/next)를 사용합니다.
원본 카톡 백업은 로컬 요구 분석 자료이며 검색 가능한 대화 아카이브로 제공하지 않습니다.

### 편집 자료 가공

`src/server/chat-pipeline/`과 `scripts/chat-*.ts`는 원본 범위·중복·최소화한 후보·보류 사유를 비공개로 관리합니다. 모델은 기술 논점을 찾고 편집하며, 코드는 원본 위치·근거 식별자·배치 범위·예산·버전을 연결합니다. 현재 전체 백업의 준비가 끝났고 나머지 후보 가공을 진행 중입니다.

가공 글은 별도의 자료편집 계정으로 표시합니다. 실제 운영자 세션의 승인, 공개본과 연결된 독립 검토, 글별 Jev 통과가 있어야 공개됩니다. 본문 수정·원자료 철회·보류·실제 처리 중지는 기존 승인을 무효화합니다. 처리 근거·권리·규칙의 참조 문자열만 바꾸면 같은 본문의 승인은 유지됩니다. 권리나 처리 조건이 실제로 바뀌어 재승인이 필요하면 먼저 `editorial_basis.allowed`를 `false`로 설정해 처리와 게시를 중지합니다. 다시 `true`로 바꿔도 새 검토·승인 없이 재공개되지 않습니다. 편집 글의 과거 기록 기간과 웹 게시일은 별개이며 가상 회원이나 댓글을 만들지 않습니다.

가공 글의 문체와 내용 선별은 작성·독립 검토가 공유하는 `src/server/chat-pipeline/editorial-policy.ts`에서 관리합니다. 특정 공개 글을 다시 검토하려면 `chat-editorial-batches.ts prepare --candidate-keys`에 비공개 키 목록을 전달합니다. 보류된 문맥을 억지로 복원하지 않으며, 새 최종본에는 새 독립 검토가 필요합니다.

대상과 기술 논점이 명확한 질문은 원자료에 답이 없어도 공개 후보로 남깁니다. 운영자가 확인한 공식 출처로 설명을 보충하려면 `prepare --supplements`에 후보별 `{ title, url, notes }` 목록이 담긴 비공개 JSON을 전달합니다. 출처는 카톡 근거와 별도로 전달하며 본문에는 `### 편집자 보충`과 해당 출처 링크를 표시합니다. 명령은 출처의 형식과 인용 여부를 검사하고, 설명의 정확성과 적용 범위는 운영자와 독립 검토자가 확인합니다. 보충으로 불명확한 프로그램이나 빠진 이미지를 추측해 메우지 않습니다.

`[링크 제거]`로 최소화한 후보의 원본 참조는 다음 로컬 명령으로 확인합니다. 입력·출력 파일은 모두 `data/chat-pipeline/` 안에 두며, 기존 파일은 덮어쓰지 않습니다. `keys.json`에는 검토할 후보 키의 JSON 배열을 넣습니다.

```sh
node --import tsx scripts/chat-editorial-references.ts inspect data/chat-pipeline/keys.json data/chat-pipeline/references.private.json
node --import tsx scripts/chat-editorial-references.ts emit data/chat-pipeline/references.private.json data/chat-pipeline/reference-decisions.private.json data/chat-pipeline/supplements.private.json
node --import tsx scripts/chat-editorial-batches.ts prepare --candidate-keys data/chat-pipeline/keys.json --supplements data/chat-pipeline/supplements.private.json
```

`inspect`는 `jobs.sqlite`를 읽기 전용으로 열고 활성 후보의 실제 질문·응답 근거에 연결된 URL 중 안전 조건을 통과한 참조만 비공개 파일에 기록합니다. 인증정보·비밀 쿼리·이메일 등 식별정보가 감지된 URL은 값 자체를 기록하지 않고 후보별 `excludedReferences` 수와 일반 사유 `unsafe-or-private-url`만 남깁니다. 원문 텍스트와 닉네임도 기록하지 않습니다. 이 단계의 안전 검사는 운영자의 확인을 대신하지 않습니다. 결정 파일은 `{ candidateKey, messageId, url, decision: "allow", checked: true, title, notes }` 항목의 JSON 배열입니다. 운영자가 해당 URL을 실제로 확인하여 안전한 공개 기술문서로 판단하고, 개인정보·비밀값·원문 표현 없이 제목과 적용 조건을 새로 작성한 경우에만 `checked: true`를 지정합니다. 제외할 참조는 `{ candidateKey, messageId, url, decision: "exclude" }`로 표시하거나 결정 파일에서 생략합니다. 확인은 운영자가 직접 수행하며 명령은 URL을 자동 허용하거나 접속하지 않습니다.

`emit`은 현재 후보·질답 근거·URL과 비공개 확인 파일이 일치하는지 다시 검사하고, 허용한 출처만 기존 `--supplements` 형식으로 출력합니다. 보류·문맥 미해결·근거 누락 후보, 선택 범위 밖 결정, 확인 누락, 위험 URL이나 감지된 비밀값·신원·원문 재사용은 출력을 차단합니다. 참조가 모두 제외되면 출력 파일을 만들지 않습니다. HTTPS 공개 DNS 주소만 허용하며 질의 문자열·fragment·퍼센트 인코딩·인증정보·내부 주소는 거부합니다. 이 검사는 사실 확인이나 익명성을 보장하지 않으므로 실제 문서의 내용과 공개 적합성은 운영자가 확인합니다. 원본 참조 목록은 모델 입력에 전달하지 않고, 검토한 출처만 `editorialSources`로 전달합니다. Windows에서는 비공개 작업 폴더의 접근 권한도 운영자가 제한합니다. 새 게시 승인 단계, DB 스키마, 별도 해시 장부나 자료 가공 비용 기록을 추가하지 않습니다.

일괄 임포트 전에는 `scripts/chat-bulk-preflight.ts`의 `prepare`와 `resolve`를 사용합니다. 비공개 manifest에 승인된 bundle/review 쌍과 선택적인 기존 글 갱신 대응표를 지정합니다. `prepare`는 공개 DB를 읽기 전용으로 조회하고 본문 블록 임베딩과 전체 비교 자료를 준비합니다. `resolve`는 그 준비 파일, 모델의 묶음 판정, 현재 공개 글 목록을 직접 비교합니다. 별도 해시 보관이나 재입력은 필요하지 않습니다. 최종본·검토 결과·비교 대상이 달라지면 새 준비 파일이 필요합니다. 불확실한 판정과 갱신될 옛 본문에 의존한 판정은 보류합니다. 비공개 작업 파일은 운영자가 관리하며, 실제 게시에는 인증·Jev·사이트 중복 검수를 적용합니다.

편집 자료에는 원래 대화 없이 이해할 수 있는 구체적인 질문·개념·조건·방법만 남깁니다. 불명확한 대상이나 필수 이미지의 빈자리를 추측하지 않으며, 대화 경과·약어 혼선·근거 없는 답변을 나열한 요약은 게시하지 않습니다. 현재 품질 기준과 같은 공개본에 대한 작성 단계·독립 검토의 통과가 필요하며, 이전 기준의 승인으로 새 게시를 통과할 수 없습니다. 품질 보류는 실제 편집 세션과 감사 기록으로 처리하고, 새 버전의 검토·승인·최종 검수를 통해 복구합니다.

가공용 CLI는 실행별로 도구와 서버 인증 환경을 제외하고, 선택한 모델·사고 수준과 예산을 기록합니다. 구독 사용률 100%만으로 크레딧 사용 불가를 단정하지 않습니다. 사용자가 크레딧 사용을 명시한 비공개 설정에서도 실제 공급자 오류와 별도 배치 상한을 적용합니다.

LLM은 Codex CLI의 실행별 토큰 기록으로 예산을 추산하고, Jev는 별도 비용 장부에서 최대 10달러를 적용합니다. 다른 세션이 함께 쓰는 계정 전체 사용률의 증분을 가공 배치 소모량으로 계산하지 않습니다. [측정 방법과 실제 처리 상태](docs/research/chat-pipeline-20261002/implementation.md)

### 데이터와 화면의 경계

서버의 조회·세션·공개 권한 판단은 `server/`가 맡습니다. `server/screens.ts`는 저장소의 결과를 `contracts/screens.ts`에 정의한 화면 데이터로 준비합니다. 화면에는 SQL 행, 인증 SDK 응답, 이메일이나 Jev 검수 근거를 전달하지 않습니다. `app/`은 이 결과에 따라 이동·404·메타데이터를 처리하고 화면과 필요한 기능을 연결합니다.

`components/screens/`와 `components/`는 전달받은 데이터·상태·이벤트를 표시합니다. API 호출, 로그인 처리와 작성 초안 저장을 직접 수행하지 않습니다. 서버에서 그리는 화면에는 작성·댓글 같은 기능을 React 요소로 전달하고, 클라이언트의 `features/` 진입점은 동작 훅의 상태·이벤트를 화면에 전달합니다.

작성·댓글·인증 동작은 `client/hooks/`, HTTP·인증 구현은 `client/`의 어댑터에 모았습니다. UI를 바꾸려면 화면 컴포넌트·토큰·스타일을 바꾸고 같은 데이터와 이벤트 계약을 연결하면 됩니다. 화면 배치나 마크업 변경 때문에 DB·Jev·인증 API·초안 복원 로직을 다시 작성할 필요가 없습니다. UI에만 필요한 펼침·초점·비밀번호 표시·로고 재생과 스크롤 상태는 화면 계층에 둘 수 있습니다.

`tests/server/layers.test.ts`는 간접 import까지 확인해 화면의 서버·클라이언트 데이터 구현 의존과 서버의 화면 의존을 막습니다. `screens.test.ts`는 세션 정보의 최소 전달, 작성자 조회, 비공개 데이터 처리와 복귀 문맥을 검증합니다. 서버 쓰기의 권한·입력 검증과 공개 전 검수는 계속 서버에서 수행합니다.

## 검증

```sh
npm run typecheck
npm test
npm run test:e2e
npm run review:ui
npm run build
```

브라우저 테스트는 별도 DB에서 헤드리스로 실행하며 실제 Jev 호출 대신 테스트 응답을 사용합니다.
첫 화면의 중복 동선, 320·390·1440px 화면의 계정 접근과 터치 영역, 탭·검색 시 스크롤 유지도 확인합니다.
브라우저 확장이 문서 루트에 붙이는 외부 속성은 `<html>`에서만 허용하며, 본문의 hydration 불일치는 계속 감지하는 회귀 테스트를 둡니다.
필요하면 `npx playwright install chromium`으로 테스트 브라우저를 설치합니다.
`JEV_MOCK`은 개발·테스트에서만 사용하고 운영 모드에서는 무시합니다.
실제 Jev 검수 기준의 정확도는 별도 평가가 필요합니다. 현재 기준은 확정된 운영 정책이 아닙니다.

게임 보안 연구 기능의 제공 범위는 [법률 검토 문서](docs/game-security-legal-review.md)에 정리했습니다.
개별 콘텐츠의 합법성 판정이나 자동 제재 정책을 확정한 문서는 아닙니다.

게시판을 나눌지와 글의 목적·주제로 찾아보는 방식은 [포럼 구조 조사](docs/research/forum-organization-20261001/report.md)에서 비교합니다.
조사 결과를 바탕으로 이번 구현은 하나의 글 목록과 질문·공유·자유 목적 필터를 사용합니다.

과거 카톡 지식을 공개하는 방식은 [가공 포스트와 주제 페이지 검토](docs/research/chat-knowledge-20261002/report.md)에 정리했습니다.
편집 포스트를 기본 자료로 두고 주제 페이지가 관련 글을 연결하는 방향입니다. 원자료 처리 근거와 개별 권리를 확인하되, 공개 당시 객관적으로 인정되는 동의 범위와 법정 예외도 검토합니다. 별도 허락이 모든 자료의 필수 조건은 아닙니다. 실제 편집·승인·게시 기능을 구현했으며 나머지 전체 자료의 가공과 게시를 진행 중입니다.

구현할 처리 순서는 [카톡 지식 편집 파이프라인 계획](docs/research/chat-pipeline-20261002/plan.md)에 정리했습니다. 코드가 파싱·중복 대응·게시 상태를 관리하고, Luna가 후보를 찾고, Sol이 재구성·근거 검토를 맡습니다. 편집 글은 같은 최종본의 편집 승인과 Jev 통과가 모두 있어야 공개하는 별도 경로로 연결합니다. 계획 검수와 실제 자료 처리·게시 기능의 검증은 구분합니다.

## 화면 구성

화면의 기준은 **공개 글 찾기 → 읽고 댓글로 참여하기 → 질문·자료 남기기 → 내 글의 공개 상태 확인하기**입니다.
첫 화면에 글 목록과 검색을 두고, 글의 목적은 질문·공유·자유로 좁힙니다. AI·도구·환경은 독립 게시판이 아닌 주제 태그입니다.
기존 분석·AI 활용 분류의 글은 공유 필터에서 함께 찾으며, 저장된 분류·주소·댓글은 바꾸지 않습니다.
주제는 본문 검색과 구별되는 정확한 태그 조건입니다. 목적·주제·검색어·페이지가 URL에 남고, 목록에서 들어간 글의 복귀 링크는 읽던 조건과 위치를 복원합니다.

| 화면            | 가장 중요한 행동                   | 배치와 문구의 기준                                                                                                                                  |
| --------------- | ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 글 목록         | 읽거나 답할 글 찾기                | 목록·검색·목적 필터를 먼저 보여 주고, 공개 글의 실제 총수와 페이지를 표시합니다. 주제는 데스크톱 오른쪽, 모바일에서는 검색 아래 펼침 메뉴에 둡니다. |
| 글 읽기         | 분석 과정 이해하고 댓글로 참여하기 | 읽기 폭을 제한하고 본문·코드·주제·사람의 댓글 순서로 읽게 합니다. 댓글 바로가기로 긴 글의 대화에 접근합니다.                                        |
| 글 쓰기         | 목적에 맞게 질문·자료 남기기       | 질문·공유·자유를 고르면 안내가 달라집니다. Markdown 미리보기와 회원별·탭별 초안 복원을 제공하고, 기본 확인 후 공개되는 흐름을 설명합니다.           |
| 내 글           | 내가 쓴 글의 공개 상태 확인하기    | 공개·공개 전 확인·공개 보류를 구분합니다. 보류를 검증 완료나 진행 중인 검수로 표현하지 않습니다.                                                    |
| 로그인·회원가입 | 하려던 작성·댓글 이어가기          | 로그인 이유와 복귀 위치를 연결합니다. 비밀번호 표시, 입력 조건, 실패 안내와 키보드 초점을 제공합니다.                                               |
| 404·오류        | 읽기 흐름으로 복귀하기             | 주소 확인·목록 이동·내 글 확인 또는 재시도를 제공합니다. 비공개 글의 존재나 내용을 드러내지 않습니다.                                               |

짙은 헤더와 회색 바탕, 얇은 구분선으로 글과 도구 화면의 구조를 구별합니다. 주요 행동에는 녹색, 질문에는 파란색, 공개 전 확인에는 황색, 공개 보류에는 적색을 사용합니다.
공개 상태는 콘텐츠의 정확성을 인증하는 표시가 아닙니다. 브랜드는 헤더에서 한 번 표시합니다.
한글 본문과 입력에는 로컬 가변 글꼴 [Pretendard](https://github.com/orioncactus/pretendard)를 사용하며, 글꼴과 SIL OFL 라이선스는 `src/app/fonts/`에 함께 보관합니다. 브랜드·코드·날짜·태그에는 고정폭 글꼴을 사용합니다.

색상·글꼴·간격·모서리·크기는 `src/app/tokens.css`에서 관리합니다.
버튼·이동 링크, 목적 표시, 주제 링크, 공개 상태와 안내문은 `src/components/ui/`의 컴포넌트를 재사용합니다.
목록·가입·작성·읽기·댓글의 화면 스타일은 `src/app/globals.css`에서 이 토큰을 사용합니다.

위키는 공동 편집·버전 관리가 필요할 때 별도 공간으로 나눕니다. AI 검증은 글 버전과 연결된 근거 영역, 호출 봇은 댓글 참여로 연결합니다. 강의·실습·CTF는 진도·제출·채점 흐름을 갖춘 별도 작업 공간으로 확장합니다. 현재 메뉴에는 동작하는 기능만 표시합니다.
화면 검수는 로컬 테스트 전용 DB에서 빈 목록·글이 쌓인 목록·필터·읽기·작성·가입·공개 상태·오류를 확인하며, 운영용 DB에 예시 글을 넣지 않습니다.
`npm run review:ui`는 66개 화면 조합의 캡처와 검수 결과를 `data/ui-ux/latest/`에 저장합니다. 저장소에는 원본 대화·계정·로컬 DB·검토 이미지가 포함되지 않습니다.

브랜드는 Reversing All입니다. 각 글자가 곡선으로 이동하며 앞·뒷면을 넘기고, 전체 이름의 뒤집힘과 복귀가 8.4초 루프로 이어집니다.
기본 이름은 한 주기에서 약 5초간 읽히며, 작은 글자 움직임과 선 강조가 이어집니다. OS 동작 줄이기 설정과 관계없이 같은 연출을 재생합니다.
왼쪽 심벌을 누르면 전체 연출을 재생하거나 정지하며, 선택은 이 브라우저에 저장합니다. 이름을 누르면 홈으로 이동합니다.
제작 근거와 검토 방법은 [로고 연출 기록](docs/research/brand-motion-20261002.md)에 정리했습니다.
