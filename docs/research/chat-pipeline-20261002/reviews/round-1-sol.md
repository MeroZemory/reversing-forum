# 독립 계획 검수 · Round 1 · Sol

2026년 10월 2일. 요청 모델·effort는 **GPT-6.1 Sol / max**이며, 실행 설정의 식별 메타데이터는 별도로 확인하지 않았다. 다른 검수자의 결과를 읽거나 에이전트를 생성하지 않았다.

대상은 [plan.md](../plan.md)의 동결 v1이다. 읽기 시작과 제출 시 SHA-256이 다음 값과 일치함을 확인했다: `bff01d9407fb31bd66ea53a333749b40541afee6fa883b0443c2333039f0520d`.

**판정: 수정 후 재검수. Critical은 발견하지 않았으며 High 2건, Medium 3건이 있다.** High 2건은 v1에서 보완할 주요 항목이고, Medium은 명세 보완과 구현 시험 조건이다. High는 실제 장애를 재현한 결과가 아니라, 계획대로 구현해도 남을 수 있는 승인·후보 식별의 경계 문제다. 합성 예제 개발은 진행할 수 있다. 실제 자료의 외부 전송·게시 준비 완료를 의미하지 않는다.

용량 정정은 별도 편집 사항이다. 사용자가 전달한 코디네이터의 파일 메타데이터 확인값은 **46,521,020 bytes(약 46.5MB)**이며, v1의 약 37MB는 v2에서 수정할 예정이다. 기존 법률 보고서의 해당 문장은 이미 정정되었다고 전달받았다. 백업을 직접 읽어 재확인하지 않았고, 동결 v1·수용 사례는 수정하지 않았다. 이 정정은 아래 주요 판정에 영향을 주지 않는다.

**법률 사실·제품 판단·미확정 사항**

공개 당시 객관적으로 인정되는 범위 안의 개인정보 처리에는 별도 동의가 불필요할 수 있다는 기존 보고서의 설명을 공식 판결과 대조했다. 공개 형태·대상·목적과 재제공 범위를 판단한다는 조건을 유지해야 한다. 이 판결을 카톡방 전체의 외부 AI 전달·웹 게시 허가로 확장하지 않은 계획은 타당하다. [대법원 2014다235080](https://law.go.kr/LSW/precInfoP.do?precSeq=183259)

아이디어와 창작적 표현을 구별하는 설명도 공식 안내와 일치한다. 개인정보의 국외 제공·조회·위탁·보관에는 별도 적용 근거를 검토하며, 국외 이전 동의만이 유일한 경로인 것은 아니다. 구체적인 자료와 계약에 대한 적합성 판단은 아직 남는다. [한국저작권위원회](https://www.copyright.or.kr/information-materials/common-sense/knowledge-for-netizen/index.do), [개인정보 보호법 제28조의8, 2026년 9월 11일 시행본](https://www.law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=08&joNo=0028&lsiSeq=283839&urlMode=lsScJoRltInfoR)

실제 편집자의 공유 글을 먼저 만들고 관련 글을 나중에 주제 안내로 연결하는 것은 제품 권고로 지지한다. 틀린 답·미확인 제안도 원래 질문과 반박을 보존하면 후보가 된다. 가상 회원·댓글·활동을 생성하지 않는 범위도 요청에 맞는다. 과거 방의 접근 조건, 개별 표현·코드의 권리와 표시 방식, 제공자별 처리 지역·계약·보관 조건은 자료·계약 확인 사항이며 이 검수로 확정하지 않는다. 내부 처리, 외부 전송, 공개를 각각 판단하는 현재 구분을 유지한다.

**S1-01 · High · 본문이 그대로여도 이용 근거 변경으로 승인을 무효화해야 한다**

위치: [§3](../plan.md#3-외부에-보낼-입력부터-제한한다), [§7](../plan.md#7-최종본을-확인한-뒤에만-공개한다), [§8](../plan.md#8-재실행수정철회가-공개를-되살리지-않게-한다), L51·95·101–105. O01에는 변경 시 무조건 재사용하지 않는다는 방향이 있지만, 게시 트랜잭션이 확인할 최신 근거 버전과 무효화 조건은 명시되지 않았다.

- **반례:** 초안 v7을 승인한 뒤 운영자가 관련 코드의 이용 근거를 미확정으로 바꾼다. 공개 본문·편집 버전·Jev 해시는 그대로이고 변경은 로컬 권리 장부에만 있다. 사이트에 남은 승인으로 게시하거나, 대기하던 외부 호출을 재개할 수 있다. 호출 캐시 키 변경만으로 기존 승인과 완료 결과가 폐기되지는 않는다.
- **최소 수정:** 승인 대상을 공개 데이터 해시와 근거·처리 범위·권리·검토 규칙의 버전 묶음으로 정의한다. 사이트 DB에 공개 가능 여부의 최신 버전을 두고, 보류 변경과 이전 승인·대기 작업 무효화를 함께 기록한다. 외부 호출·캐시 사용 직전과 게시 트랜잭션에서 최신 허용 범위를 다시 검사한다. 로컬 증거 전체를 사이트에 복제할 필요는 없다.
- **수용 조건:** O01/W03/W05에 ‘본문 불변, 근거만 변경’을 추가한다. Jev 대기 중 변경, 캐시 재사용, 오래된 게시 요청 모두 이전 승인으로 진행하지 않아야 한다. 이미 공개된 관련 글에는 운영자가 정한 비공개·재검토 조치를 연결한다. 이는 계획상의 보류 정책이며 모든 허락 변경이 법률상 같은 효과를 낸다는 주장은 아니다.

**S1-02 · High · 요청 멱등성과 대화 후보의 동일성은 별도로 연결해야 한다**

위치: [§2](../plan.md#2-겹친-백업을-별개의-동의나-답변으로-세지-않는다), [§4](../plan.md#4-후보를-넓게-찾고-맥락을-복원한다), [§8](../plan.md#8-재실행수정철회가-공개를-되살리지-않게-한다), L47·61·101·107. 메시지 대응 보존과 같은 게시 요청의 영수증은 있지만, 겹친 묶음·재추출에서 생성된 후보를 기존 후보/글로 연결하는 규칙은 없다.

- **반례:** 동일한 질문 Q와 응답 A가 겹친 두 묶음에서 C1={Q,A}, C2={Q,A,반박}으로 추출된다. 서로 다른 후보·게시 요청에는 각각 영수증이 생겨 글이 두 개가 된다. C1을 철회한 뒤 재실행에서 새 C2가 생성되면 기존 후보의 철회 상태만 확인하는 구현은 같은 자료를 다시 게시할 수도 있다.
- **최소 수정:** 모델이 제안한 ID를 그대로 영속 후보 ID로 사용하지 않는다. 정규 메시지의 질문·논점 기준으로 중복 가능 후보를 모으고, 첫 배치는 편집자가 기존 후보와 연결하거나 의도적 분할을 지정한다. 후보 ID와 기존 글 ID의 대응, 병합된 ID, 철회 식별 기록을 재실행에도 유지한다. 사이트에는 후보→글의 유일성과 후보·버전별 요청 키를 두며, 같은 키의 다른 데이터는 거절한다.
- **수용 조건:** D01/W04/W05를 겹친 입력 묶음·프롬프트 변경·응답 유실 후 재실행까지 확장한다. 같은 논점의 재추출은 기존 글로 연결되고 철회를 우회하지 않아야 한다. 다른 날 실제로 반복한 질문이나 편집자가 지정한 별도 사례는 독립 후보로 남아야 한다. 자동 의미 병합기를 먼저 만들 필요는 없다.

**S1-03 · Medium · 주장 근거에는 실제 사용한 구간과 연결 관계가 필요하다**

위치: [§1](../plan.md#1-원본을-읽되-버리지-않는다), [§4](../plan.md#4-후보를-넓게-찾고-맥락을-복원한다), [§5](../plan.md#5-글을-만들면서-근거를-잃지-않는다), L39·61–71. 원본의 메시지 위치는 보존하지만 주장 장부의 근거는 메시지·문서 단위로만 설명되어 있다.

- **반례:** 한 긴 메시지에 ‘환경 A에서는 실패했고 환경 B에서는 성공했다’가 함께 있다. ‘A에서 해결됐다’는 초안도 존재하는 메시지 ID를 참조할 수 있다. 분할 입력이나 삭제된 식별 맥락 때문에 검토자가 본 구간과 원문 장부의 구간이 달라도 ID 검사만 통과한다.
- **최소 수정:** 주장마다 근거의 관련 구간, 원본 출현/정규 메시지 대응 버전, 모델에 실제 전달한 변환본의 해시, 지지·반박·맥락 관계와 연결 불확실성을 남긴다. 짧은 메시지는 전체를 구간으로 쓸 수 있다. 공식 문서는 확인한 절·버전을 연결한다. 코드가 지지 여부를 판정하게 하지 않고 검토자가 확인할 위치를 정확히 제시한다.
- **수용 조건:** E02/E03/E04에 한 메시지의 상반된 환경·교차 답변·분할 경계 사례를 추가한다. 엉뚱한 환경의 결과와 누락된 반박은 검토에서 거절하고, 실제 전달 구간에서 원본 위치까지 역추적되어야 한다. 익명화로 연결 정보가 부족해지면 불확실성을 남긴다.

**S1-04 · Medium · 맥락 확장에도 전송 범위와 요청 상한을 적용해야 한다**

위치: [§3](../plan.md#3-외부에-보낼-입력부터-제한한다), [§4](../plan.md#4-후보를-넓게-찾고-맥락을-복원한다), [§8](../plan.md#8-재실행수정철회가-공개를-되살리지-않게-한다), L53–63·103. 제한된 묶음과 예산 중단 원칙은 있지만 긴 단일 메시지·추가 문맥·재시도를 포함한 호출 전 검사와 초과 처리 규칙은 아직 없다.

- **반례:** 작은 Luna 입력의 후보가 Sol에서 앞뒤 문맥을 요구한다. 추가 구간에는 아직 허용하지 않은 개인 사례가 있거나 요청 상한보다 긴 코드가 있다. 앞부분만 잘라 보내면 끝의 반박이 사라지고, 동시 요청의 비용을 완료 후에만 계산하면 예산을 넘겨 호출할 수 있다.
- **최소 수정:** 모든 Luna/Sol/Jev 호출이 같은 전송 검사기를 거치게 한다. 추가 구간에도 최신 처리 범위·최소화 규칙을 적용하고, 제공자별 요청 바이트·입력/출력 토큰·누적 맥락 확장·재시도 상한과 호출 전 예산 확인을 설정한다. 초과 시 구간을 추적하며 나누거나 보류하고, 조용히 잘라 완료 처리하지 않는다. Jev에는 최종 공개본 전체가 들어가지 않으면 통과로 처리하지 않는다.
- **수용 조건:** 합성 장문, 허용 범위 밖의 인접 발언, 예산 소진, 재시도 요청을 검사한다. 허용되지 않은 구간은 외부 호출이 없어야 하고, 분할로 빠진 맥락은 표시되어야 한다. 정확한 수치와 공급자 제한은 구현·계약 확인 사항이다. 확인한 Jev OpenAPI의 `state`에는 `maxLength`가 없으므로 실제 무제한 입력을 뜻한다고 추정하지 않는다. [Typesafe OpenAPI 0.2.0](https://api.typesafe.ai/openapi.json)

**S1-05 · Medium · Sol/xhigh를 거치는 조건이 문서 안에서 충돌한다**

위치: [코드와 모델의 역할](../plan.md#코드와-모델의-역할), [§5](../plan.md#5-글을-만들면서-근거를-잃지-않는다), L28·33·71.

- **반례:** L33의 ‘애매하거나 검토 누락이 반복되는 사례만 xhigh’를 따르면 쉬운 후보는 medium 초안에서 편집자·Jev로 바로 갈 수 있다. L71과 사용자가 지정한 근거·위험 검토 경로는 다른 해석을 준다. 대화 연결이 쉬워도 권리·재식별 문제가 없다는 뜻은 아니다.
- **최소 수정:** 공개 대상 최종 초안은 Sol/xhigh의 근거·위험 검토를 거치도록 문구를 통일한다. 애매한 추출·연결의 추가 검토와 구분하고, 공개하지 않을 모든 후보에 xhigh를 요구하지 않는다. max는 독립 계획 검수에만 유지한다.
- **수용 조건:** 쉬운 후보와 복잡한 후보 모두 해당 최종 버전의 검토 기록이 있어야 한다. xhigh 접근 불가 시 계획의 보류 규칙을 적용한다. 이 기록이나 Jev 통과를 기술적 정답·법률상 허가로 표시하지 않는다.

**작은 구현으로 유지할 범위**

로컬 CLI, 비공개 초안 한 화면, 실제 운영자 한 명, 사이트 DB의 버전·승인·영수증으로 충분하다. 별도 서비스·벡터 DB·상시 max 검수 조직을 미루는 선택에 동의한다. 버전 조건과 철회·영수증은 소규모에도 필요하다. 첫 합성 예제 한 건을 파싱부터 초안 확인·게시 조건·철회까지 연결한 뒤 배치 범위와 평가를 넓히면 usable flow를 빨리 확인할 수 있다. 후보의 전자동 의미 병합, 주제 안내, 정기 재검증은 실제 필요에 따라 확장한다. 90%/95%는 측정 전 목표이며 10~20건의 검토만으로 대규모 자동 게시를 열 근거가 되지 않는다.

현행 코드에서 `createPost`는 Jev 결과를 글 상태에 반영한다(`forum.ts:248–285`). DB에는 편집 버전·승인·영수증 테이블이 없고(`db.ts`), 화면 계약에도 편집 출처·주장 상태가 없다. 따라서 §7의 별도 편집 경로와 필요한 표시 계약 확장은 구현 시 확인해야 한다. 기존 일반 글 경로를 그대로 사용하면 된다는 주장은 하지 않는다. Jev 어댑터는 현재 실제 모델·usage·검사 해시를 보존하지 않으며, 계획이 이 보완 필요성을 이미 밝힌 점도 확인했다.

**검증과 한계:** 원본 카톡 백업, `.env`, 인증 폴더·키, 다른 검수자의 출력은 읽지 않았다. 실제 자료 처리·모델 검수 호출·게시는 수행하지 않았다. 파이프라인 런타임 테스트, 타입 검사, 앱 빌드, 브라우저 시험은 실행하지 않았다. 수행한 검증은 문서·코드 대조, 공개 공식 출처 조회, 동결 해시와 제출 파일의 구조·참조 확인이다. 합법성·재구성 정확도·회수율·경쟁 조건의 실제 보장은 해당 자료·계약·구현 시험을 통해 확인해야 한다.
