# 카톡의 지식을 편집 글로 만드는 파이프라인

2026년 10월 2일 · 초안 v1 · 계획과 검수 범위

## 만들려는 결과

카톡에 실제로 오간 질문·제안·반박·결과 보고를 읽기 좋은 편집 글로 만들고, Reversing All의 기존 글 목록·주제 태그·댓글에 연결합니다. 답변이 틀리거나 결론이 나지 않았더라도 가치 있는 대화는 후보입니다. 확인되지 않은 답을 성공 사례나 정답으로 바꾸지 않습니다.

기본 산출물은 **편집 책임자가 있는 하나의 글**입니다. 관련 글이 쌓이면 같은 글들을 주제 안내 페이지에서 연결합니다. 원문 검색, 참여자별 분석, 가상의 회원·댓글·좋아요는 만들지 않습니다. 과거 대화 시점과 실제 웹 게시 시점을 구분합니다. 지금 계획하는 것은 가공·게시 절차이며, 이 문서 작성 중에는 원문을 외부 모델에 보내거나 사이트에 게시하지 않습니다.

첫 구현은 **로컬 배치 도구 → 비공개 편집 초안 → 실제 편집자의 확인 → Jev 확인 → 공개 글**입니다. 기존 TypeScript·SQLite·인증·글 표시 계층을 사용합니다. 별도 서비스, 벡터 DB, 상시 돌아가는 다중 에이전트 조직은 필요해질 때 TODO에 추가합니다.

## 전제와 처리 범위

- 사용자는 공개 카톡방이라고 설명했으며, 웹 재사용·외부 AI 처리에 대한 별도 사전 동의나 공지는 없었다고 확인했습니다. 과거 시기별 검색·가입·접근 조건은 아직 확인하지 않았습니다.
- 다섯 백업은 약 37MB이며 일부 시기가 겹칩니다. 서로 다른 두 내보내기 형식과 BOM 유무가 있습니다. 닉네임 변경과 첨부 자료 누락이 있을 수 있습니다. 전 기간이 연속된 기록이라고 가정하지 않습니다.
- [법률·제품 검토](../chat-knowledge-20261002/report.md)를 따릅니다. 공개 정보에 새로운 개별 동의가 언제나 필요한 것은 아닙니다. 대법원 2014다235080의 객관적으로 인정되는 공개 당시 동의 범위, 정당한 이익 등 실제 처리 근거를 검토할 수 있습니다. 기술적 사실·아이디어와 보호되는 표현의 이용은 구분합니다.
- 원자료의 로컬 처리, 외부 AI 전달, 최종 웹 공개는 각각 범위와 근거를 기록합니다. 글에서 닉네임을 제거했다는 이유로 원자료 처리나 국외 이전까지 해결됐다고 판단하지 않습니다. 원문 대응표를 보유하는 자료를 자동으로 익명정보로 선언하지 않습니다.
- 처리 근거는 적합한 자료 범위에 대해 묶어서 기록할 수 있습니다. 매 메시지마다 800명 전원의 동의를 받는 절차를 기본으로 두지 않습니다. 보호되는 코드·설명·개인 사례·제3자 정보의 예외는 해당 후보에서 따로 확인합니다.

모델 호출은 사용자가 지정한 조합을 사용하며 프로젝트·전역 모델 설정을 바꾸지 않습니다. 중립적인 작업 평가는 후보 찾기가 fast/measured, 재구성이 standard/thorough, 근거·권리 경계 판단이 frontier/thorough입니다. 독립 max 검수는 사용자의 명시 요청입니다. 쉬운 형식 작업은 코드로 내려 비용을 줄이고, 연결이 애매하거나 검토 누락이 반복되는 사례만 xhigh로 올립니다. 검토가 어려운 사례는 사람에게 넘깁니다.

## 1. 원본을 읽되 버리지 않는다

원본 파일은 접근을 제한한 로컬 `data/chat-pipeline/` 아래에서 다룹니다. 저장소·빌드 산출물·공개 정적 파일·모델 로그에 넣지 않습니다. 기존 루트 백업의 위치를 바꾼다고 가정하지 않고, 파일 경로와 SHA-256 및 파서 버전을 비공개 manifest에 기록합니다. 파일명에도 개인 정보가 있을 수 있으므로 공개 산출물에 복사하지 않습니다.

파서는 UTF-8/BOM과 두 내보내기 형식을 구분하고, 날짜 경계·시각·여러 줄 본문·시스템 메시지·첨부 표시를 추출합니다. 원본 바이트 범위와 행 범위, 원본 순서, 시각의 정밀도를 남깁니다. 없는 초 단위 시간을 생성하지 않습니다. 코드·디스어셈블리·경로의 공백과 기호는 의미를 바꿔 정규화하지 않습니다.

인식하지 못한 행은 제외 목록에 보관합니다. 모든 입력 범위가 메시지·내보내기 헤더·시스템 항목·미해석 구간 중 하나에 대응하는지 코드로 확인합니다. 미해석 구간과 첨부 누락이 있는 묶음은 모델이 완전한 대화라고 믿지 않도록 표시합니다. 닉네임은 각 발언의 원본 표기만 보관하며, 이름이 같거나 바뀌었다는 이유로 사람을 통합하지 않습니다.

## 2. 겹친 백업을 별개의 동의나 답변으로 세지 않는다

원본의 각 출현은 독립적으로 보존합니다. 다른 백업 사이의 날짜·본문·주변 발언 순서를 이용해 겹치는 구간을 정렬하고, 충분히 일치하는 출현들만 같은 메시지 후보로 묶습니다. 본문 해시 하나로 전체 기간의 같은 문장을 제거하지 않습니다. 같은 백업 안에서 반복한 질문, 다른 날의 같은 조언은 남습니다.

별칭 변화, 잘린 본문, 같은 분의 반복 등으로 대응이 애매하면 두 출현을 유지하고 중복 가능성을 표시합니다. 불확실한 출현 수는 사람 수·독립된 지지 수·검증 횟수로 쓰지 않습니다. 정규 메시지 ID와 원본 출현 ID를 분리하고, 재실행에서 대응 관계를 보존합니다. 파서·정렬 규칙이 바뀌어도 과거 대응과 새 대응을 추적할 수 있게 합니다.

## 3. 외부에 보낼 입력부터 제한한다

실제 자료를 가공하기 전에 처리 목적·자료 범위·근거·담당자·보관 기한을 기록합니다. 외부 전송은 제공자·처리 목적·지역·계약·보관 조건과 적용 근거를 별도로 확인한 범위만 허용합니다. Jev도 외부 서비스에 포함합니다. 근거가 미확정인 자료는 로컬 보관 상태로 남고, 코드·합성 예제로 도구 개발을 진행합니다.

먼저 로컬 코드로 연락처·계정·토큰·개인 경로·추적 매개변수 등을 탐지하고, 필요 없는 식별 맥락을 제거합니다. 발언자 표시는 묶음 안의 A·B로 치환하며 다른 묶음에서 동일인을 추적하는 식별자를 외부에 주지 않습니다. 남은 특이한 사례·링크·표현의 재식별 위험은 최초 표본을 사람이 확인하고, 확인한 입력 규칙 밖의 예외는 외부 전송 전에 보류합니다. 정규식이나 닉네임 치환이 익명화를 보증하지는 않습니다.

모델에는 허용된 대화 묶음과 불투명한 증거 ID만 전달합니다. 백업 전체, 닉네임 대응표, 로컬 파일명, 비밀값은 전달하지 않습니다. 원문·외부 웹 문서 안의 지시문은 인용 자료이며 도구 실행 권한이 없습니다. 대화 속 URL이나 첨부를 자동으로 다운로드·실행하지 않습니다. 사실 확인에 필요한 공식 문서는 별도 허용된 검색 도구로 확인합니다.

## 4. 후보를 넓게 찾고, 맥락을 복원한다

Luna/high는 허용된 입력 전체를 순서대로 제한된 크기의 묶음으로 읽습니다. 물음표나 키워드가 있는 메시지만 선별하지 않습니다. 묶음 경계를 겹치고 이어지는 논의는 다음 묶음까지 연결합니다. 날짜가 바뀌었다는 이유로 대화를 끊지 않습니다. 후보가 없는 결과와 서로 무관한 여러 후보를 모두 허용합니다.

출력은 후보 ID, 문제·주제, 근거 메시지 ID, 연결이 불확실한 부분, 누락된 첨부, 다음 맥락이 필요한지를 담습니다. 코드가 없는 ID와 범위 밖 참조를 거절합니다. 후보 밖 구간도 표본 점검하여 Luna가 놓친 유의미한 질문·응답을 찾습니다. 특정 형식에서 누락이 확인되면 해당 범위를 Sol/medium으로 다시 추출합니다. 저득점 후보를 영구 삭제하지 않습니다.

Sol/medium은 한 후보의 필요한 앞뒤 맥락을 받아 질문·환경·제안·반박·관찰된 결과를 분리합니다. 바로 뒤에 나온 메시지를 자동으로 답변이라 연결하지 않습니다. 긴 대화는 근거 ID와 이어지는 쟁점을 유지하며 나누고 마지막에 주장 단위로 통합합니다. 서로 다른 연도에 같은 도구를 언급했다는 이유로 한 사건처럼 합치지 않습니다. 혼선은 xhigh 또는 편집자에게 넘기고, 답을 만들어 채우지 않습니다.

## 5. 글을 만들면서 근거를 잃지 않는다

각 기술 주장은 비공개 장부에 다음 중 하나의 근거를 갖습니다: 원대화 메시지, 확인한 공식 문서, 편집자가 작성한 자작 예제·재현 기록. 공식 문서를 추가했다면 원대화에서 나온 주장과 구분합니다. 인용 가능한 자료가 없거나 재현하지 못한 경우에도 ‘당시 제안’으로 남길 수 있습니다. “실제로 해결됐다”는 표현은 그 결과가 보고되거나 재현된 경우에만 사용합니다.

주장 상태는 `당시 제안 / 당시 결과 보고 / 현재 문서 확인 / 현재 재현 / 상충 / 미확인`으로 기록합니다. 결과 보고 자체가 현재 재현은 아닙니다. 오래된 API·도구 버전·운영체제는 확인한 범위를 함께 적고, 현재성 검토일을 표시합니다. 글 전체에 단일 ‘정확도 95%’나 ‘검증 완료’ 표시를 붙이지 않습니다.

Sol/xhigh는 초안과 근거를 따로 비교하여 없는 결론·잘못 연결한 답변·사라진 반박·식별 정보·보호되는 표현 및 실제 게임 서비스에 대한 작동 지원 위험을 검토합니다. 현재 기술 사실을 확인할 필요가 있으면 공식 문서와 재현 기록을 근거로 삼습니다. 모델끼리 동의했다는 사실은 기술적 검증이나 이용허락의 근거가 아닙니다.

초기 산출물은 문제·환경, 제안과 이유, 반박·미해결 부분, 현재 확인 범위, 참고 자료를 필요에 따라 담습니다. 모든 글에 긴 양식을 강제하지 않습니다. 질문과 답변이 있는 대화도 과거 질문자를 현재 회원처럼 표시하지 않고, 편집 책임자의 ‘공유’ 글로 시작합니다. 공개 분류와 주제 태그는 현재 사이트의 계약을 사용합니다.

## 6. 이용 방식과 공개 승인을 분리한다

| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 일반 기술적 사실·아이디어                   | 적법한 원자료 처리 범위에서 독립 설명·자작 예제로 작성합니다. 원대화를 그대로 재현했다고 표시하지 않습니다.                                                    |
| 보호되는 설명·코드·이미지                   | 이용허락·라이선스 또는 구체적으로 검토한 법정 예외와 출처 표시가 있어야 사용합니다. AI로 바꾸어 썼다는 이유만으로 통과하지 않습니다.                           |
| 실제 개인 사례·식별 정보                    | 별도 동의가 유일한 경로라고 단정하지 않되, 공개 근거와 필요성을 확인하고 불필요한 식별을 제거합니다.                                                           |
| 게임 치트·상용 서비스 우회·판매·악성 실행물 | Jev와 별도로 [게임 보안 법률 검토](../../game-security-legal-review.md)에 따라 보류·검토합니다. 초기에는 범용 도구·자작 및 허가된 예제·방어 연구를 우선합니다. |
| 원문 없이 재작성한 독립 기술 설명           | 공식 문서·자작 예제에 근거하고 출처를 표시합니다. 가상의 원대화나 해결 사실을 붙이지 않습니다.                                                                 |

외부 모델은 예외를 찾아 설명할 수 있지만, 법률 판단을 승인 값으로 발급하지 않습니다. 인용·공정 이용에 따른 공개 출처 표시가 개인정보 보호와 충돌하면 게시 전에 해결하거나 보호되는 표현을 사용하지 않는 설명으로 대체합니다. 내부 대응표는 공개 출처 표시 의무를 대신하지 않습니다. 질문자의 허락으로 답변자·제3자의 권리까지 해결됐다고 처리하지 않습니다.

첫 배치는 후보 10~20건을 편집자가 원문 근거와 비교하여 검토합니다. 이는 품질과 운영을 확인하기 위한 시작 규모이며 법률상 동의가 항상 필요한 수량이라는 뜻이 아닙니다. 적합한 건만 게시하고, 적합한 글이 적으면 수량을 맞추려고 가공하지 않습니다.

## 7. 최종본을 확인한 뒤에만 공개한다

공개용 데이터와 비공개 근거는 별도 구조로 저장합니다. 공개용은 제목·본문·글 목적·태그, 편집 책임자, 출처 유형, 필요한 공개 출처, 과거 자료 시기, 주장 상태·확인일입니다. 비공개는 원본 위치·발언 대응·처리 근거·권리 자료·모델 입출력·비용·Jev 응답·승인 기록입니다. 공개 조회는 공개 필드의 허용 목록만 반환합니다.

코드는 최종본의 필수 필드·길이·참조·출처·금지된 식별값·링크 및 Markdown 정책을 검사합니다. Jev는 **화면과 검색에 노출될 최종 공개 내용 전체**를 검사합니다. 현재의 spam/harassment/privacy와 fail-closed 동작을 유지하되 0.90 기준을 정확도 90%로 설명하지 않습니다. 요청한 `jev-latest`와 응답의 실제 모델, 규칙 버전, 검사 대상 해시를 비공개로 남깁니다. 현재 어댑터에는 이 메타데이터가 모두 구현되어 있지 않습니다.

공개 조건은 같은 편집 버전에 대해 **처리·권리 검토 완료 + 근거 검토 완료 + 편집자 승인 + 최종 Jev 통과 + 코드 검사 통과**입니다. 글을 고치면 내용 해시가 바뀌어 이전 승인을 사용할 수 없습니다. API 오류·응답 형식 오류·미확정 판단은 비공개로 남습니다. 오류 재시도는 최초 2회까지로 시작하고, 위반 결과가 나왔다는 이유로 통과할 때까지 재호출하지 않습니다.

현재 `createPost`는 일반 회원의 글을 `pending`으로 저장한 뒤 Jev 통과 시 바로 공개합니다. 편집 초안에는 이 경로를 그대로 쓰지 않습니다. 새 비공개 편집 초안 등록·검토·공개 함수를 만들고 기존 Jev 및 표시 계약을 재사용합니다. 실제 서버 세션으로 편집 책임자와 편집 권한을 확인합니다. CLI가 임의의 Viewer를 구성하거나 DB에 `published`를 직접 삽입하지 않습니다. 초기 편집 권한은 실제 운영자 한 명으로 제한하고 모든 서버 쓰기에서 검사합니다.

## 8. 재실행·수정·철회가 공개를 되살리지 않게 한다

작업 데이터는 로컬 비공개 SQLite에서 관리할 수 있습니다. 최종 게시 영수증은 사이트의 같은 DB에 두고, 하나의 트랜잭션 안에서 후보·버전·해시·승인·현재 상태를 확인하여 공개 글과 영수증을 함께 만듭니다. 공개 글 ID만 로컬에 기록한 뒤 다시 실행하면 중복되는 구조를 피합니다. 동일 게시 요청은 기존 영수증을 반환하고, 내용 수정은 같은 글의 새 버전으로 연결합니다. 별개의 실제 대화는 본문이 같다는 이유만으로 같은 글로 합치지 않습니다.

파서·모델·프롬프트·스키마·입력 해시·검토 규칙·처리 범위 버전을 호출 캐시 키와 이력에 남깁니다. 모델 출력은 스키마 검증뿐 아니라 근거 ID·상태 전이 검증을 통과해야 합니다. 거절·잘린 출력·유효하지 않은 JSON은 재구성 완료로 처리하지 않습니다. 모델 접근이 없으면 다른 모델로 몰래 교체하지 않고 해당 작업을 보류합니다. 첫 실행 동시 호출은 1~2개로 제한하고 예산 초과 시 새 호출을 중단합니다.

철회는 재시도·지연 중인 검수를 취소하는 상태를 먼저 기록하고 공개 글을 비공개로 전환합니다. 늦게 도착한 Jev 결과가 과거 버전을 다시 공개하지 않도록 버전·상태를 조건으로 갱신합니다. 재실행도 철회 상태를 존중합니다. 공개 수정도 새 버전의 전체 공개 조건을 다시 확인합니다. 초기에는 수정 동안 글을 비공개로 두는 단순한 방식을 사용합니다.

권리침해·정정 요청에는 대상 글, 파생 안내·검색·메타데이터·사이트맵·우리가 통제하는 캐시를 함께 점검합니다. 확인 기록에 삭제한 개인 내용을 다시 복제하지 않습니다. 원자료·권리 자료·모델 로그의 보관 목적과 기한을 정하고, 파기 시 같은 자료로 재수집·재게시하지 않도록 필요한 최소 비내용 기록을 남깁니다. 외부 검색·AI가 저장한 모든 사본까지 삭제됐다고 약속하지 않습니다.

## 단계별 구현과 검증

| 순서 | 구현할 범위                                                                           | 완료를 확인하는 방법                                                                           |
| ---- | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| A    | 합성 예제 기반 파서·중복 대응·비공개 작업 저장·검증 명령                              | [수용 사례](acceptance.md)의 형식·반복·경계·누락 사례와 결정론적 재실행                        |
| B    | 근거 있는 입력 범위와 외부 전송 조건 기록, 최소 입력 변환, 모델 어댑터·후보/초안/검토 | 허용한 작은 표본의 사람 기준표와 비교; 누락·잘못 연결·만든 결론·재식별·토큰 비용 측정          |

평가 표본은 형식·연도·대화 길이·중첩 여부를 나누고 후보 밖 구간도 포함합니다. 기준표를 만드는 표본과 마지막 확인 표본은 구분합니다. 초기 운영 제안은 의미 있는 후보 회수율 90% 이상, 질문·답 연결 정확도 95% 이상이며 실제 측정 전의 목표입니다. 어느 수치든 근거 없는 성공·실제 식별 정보·비밀값의 공개, 권한 우회, Jev 실패 후 공개, 철회 후 재공개는 한 건도 허용하지 않습니다. 표본이 작으면 수치만으로 일괄 자동 게시를 열지 않습니다.

구현 전 비용 한도를 정확한 금액으로 추정하지 않습니다. 첫 작은 배치에서 단계별 입력·출력·추론 토큰, 재호출, 지연, 사람 검토 시간을 기록하고 전체 자료 처리 예산을 추정합니다. 원문 대신 개수·ID·요약 오류 코드만 일반 로그에 남깁니다. 원문이 포함된 상세 응답은 비공개 접근·보관 규칙을 적용합니다.

## 검수 방식과 현재 한계

각 라운드는 같은 고정 초안을 Sol/max와 Astra/max가 서로의 결과를 보지 않고 읽습니다. 검수자는 원본 카톡·비밀값을 받지 않으며 계획·법률 보고서·관련 코드만 봅니다. 기능 의도, 의미 보존, 개인정보·권리 경계, 게시 경쟁 조건, 비용과 과잉설계에 대해 반례와 수정 사항을 제출합니다. 중요한 지적을 반영한 새 버전은 두 모델이 다시 독립 확인합니다. 남은 차이는 투표로 지우지 않고 근거·구현 시험·사람 판단 항목으로 남깁니다.

종료 조건은 계획에서 해결 가능한 중대한 결함이 없고, 실제 자료·계약·구현 시험이 있어야 확인할 항목이 작업 순서와 중단 조건에 반영된 상태입니다. 검수 통과는 아직 만들지 않은 파서의 정확도나 개별 글의 합법성을 증명하지 않습니다. 실제 파싱·대화별 권리 확인·모델 실행 평가·게시 기능은 위 단계로 구현할 작업입니다. 검수 결과와 수정 내역은 [검수 기록](review-log.md)에 별도로 남깁니다.
