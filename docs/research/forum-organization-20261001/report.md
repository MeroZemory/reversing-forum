# Reversing All 게시판과 필터 구조 조사

Reversing All을 위한 2026년 10월 1일 조사입니다. 초기 웹 이용자 약 100명이라는 예상, 자유로운 사람의 대화와 Q&A, 웹에서 정보의 정리·검증·재사용을 돕는다는 방향을 기준으로 검토했습니다. 가입자·활성 회원·일일 방문자 수와 실제 글 발생량은 아직 측정되지 않았습니다.

**현재의 제안은 전체 글을 함께 볼 수 있게 유지하면서, 답할 질문과 다시 쓸 자료를 쉽게 찾게 하는 구조입니다.** 목적 필터를 두는 안은 유력한 후보이지만, 분류 없이 시작하는 안과 이름 있는 소수 게시판을 두는 안보다 우수하다고 입증된 것은 아닙니다. AI 리버싱이나 정리 자료의 진입점도 실제 콘텐츠가 준비되어 있다면 첫 공개부터 제공할 수 있습니다.

이 문서는 실제 사례, 구조별 대안, 첫 화면과 작성 흐름, 이후 분리할 조건을 비교합니다. 애플리케이션 변경에 앞서 큰 방향을 검토하기 위한 제안입니다. [출처와 조사 한계](sources.md)를 함께 읽을 수 있습니다.

요청한 Astra/max와 6.1 Sol/max의 독립 검수 지적은 [검수와 반영 결과](review-summary.md)에 정리했습니다. 검수에 따라 단일 목적 분류의 한계와 이름 있는 공간의 가치를 보완했습니다.

## 먼저 구분해야 하는 다섯 가지

이 구분은 사용자가 글을 쓸 때 다섯 항목을 채우라는 뜻이 아닙니다. 서로 다른 역할의 정보를 하나의 탭에 넣어 혼란을 만들지 않도록 내부 판단을 정리한 것입니다.

| 구분           | 답하는 질문                        | 예시                                                     | 제안하는 사용 방식                                                         |
| -------------- | ---------------------------------- | -------------------------------------------------------- | -------------------------------------------------------------------------- |
| 글의 목적      | 작성자가 지금 어떤 반응을 원하는가 | 도움 요청, 설명과 결과물 공유, 의견과 대화               | 한 가지 주된 목적을 고르거나, 분류 없는 대안과 비교합니다.                 |
| 주제와 환경    | 무엇에 관한 글인가                 | Ghidra, Windows, ARM64, 악성코드 분석, AI 리버싱         | 한 글에 겹칠 수 있으므로 태그와 검색으로 연결합니다.                       |
| 내용 형식      | 무엇을 읽거나 사용하는가           | 분석 기록, 튜토리얼, 링크, 도구 소개                     | 처음부터 모두 필수 입력이나 독립 게시판으로 만들지 않습니다.               |
| 상태           | 지금 어떤 진행 단계인가            | 공개 여부, 피드백 요청, 사람의 해결 확인, 특정 버전 검수 | 각 상태를 만든 근거가 있을 때만 표시합니다. 일반 태그로 증명하지 않습니다. |
| 별도 작업 공간 | 글과 댓글을 넘어 무엇을 하는가     | 공동 편집 위키, 수강과 진도, CTF 제출과 채점             | 실제 작업 방식과 권한이 달라질 때 별도 기능으로 만듭니다.                  |

예를 들어 ‘AI가 만든 Ghidra 분석이 맞는지 봐 주세요’는 도움을 원하는 질문이며 AI·Ghidra·대상 환경에도 속합니다. 이를 AI 게시판과 질문 게시판 중 하나에만 넣게 하면 다른 경로에서 누락될 수 있습니다. 반대로 AI 분석 작업법을 체계적으로 가르치는 공간은 별도의 목적과 편집 방식이 생길 수 있습니다. 따라서 **AI를 무조건 독립 게시판으로 두거나 무조건 단순 도구 태그로 축소하는 결론 모두 피합니다.**

## 선택할 수 있는 여섯 가지 구조

아래 장단점은 사례와 현재 요구에서 도출한 설계 판단입니다. 우리 회원에게 검증된 결과나 수치화된 우열은 아닙니다.

| 대안                          | 사용자가 보는 모습                                                                          | 장점                                                                                                         | 부담과 선택 조건                                                                                                                                                                            |
| ----------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A 분류 없는 공통 목록         | 전체 글, 검색, 필요한 태그만 있습니다.                                                      | 쓰기 전에 종류를 고민하지 않아도 됩니다. 혼합된 글을 받아들이기 쉽습니다.                                    | 답해 줄 질문과 읽을 자료를 바로 구별하기 어렵습니다. 목적 선택을 뺐을 때 작성 부담이 줄고 필요한 글도 충분히 찾을 수 있다면 적합합니다.                                                     |
| B 공통 목록과 목적 필터       | 전체에서 질문·공유·자유를 골라 보고, 주제는 태그로 찾습니다.                                | 질문에 답하기, 자료 읽기, 대화하기를 짧은 경로로 연결합니다. 주제 중복도 수용합니다.                         | ‘공유’와 ‘자유’의 경계가 애매할 수 있습니다. 예시를 보고 작성자가 일관되게 고르는지 확인해야 합니다. **유력한 비교 후보이며 회원 사용으로 검증되지 않았습니다.**                            |
| C 목적별 소수 게시판          | 질문, 분석과 자료, 자유 게시판이 있고 전체 글도 있습니다.                                   | 게시판마다 목적과 작성 안내를 분명하게 보일 수 있습니다.                                                     | 질문이 분석으로 발전할 때 이동·연결 방식을 정해야 합니다. 기능 차이뿐 아니라 이름·설명·대표 글·공동 활동의 위치가 필요한 경우에 검토합니다.                                                 |
| D 주제별 게시판               | Windows·Android·게임 보안·악성코드·AI 등으로 나눕니다.                                      | 특정 분야를 계속 찾는 집단이 머무를 공간이 생깁니다.                                                         | 하나의 글이 여러 주제에 해당합니다. 어디에 쓸지 갈리고, 반복 게시나 발견 누락을 관리해야 합니다. 분야별 참여자가 뚜렷할 때 검토합니다.                                                      |
| E 공통 목록과 주제별 모아보기 | 전체와 목적 필터 위에 ‘AI 리버싱’, ‘입문 자료’, ‘게임 보안 연구’ 등 필요한 진입점을 둡니다. | 독립 게시판 없이도 중요한 주제를 쉽게 발견하게 합니다. 태그 조건 또는 운영자가 고른 글로 구성할 수 있습니다. | 자동 목록과 편집한 모음의 차이를 설명해야 합니다. 처음부터 모든 주제를 메뉴로 올리면 다시 복잡해집니다. A·B·C와 결합할 수 있고, 실제 자료가 있으면 초기부터 작은 형태로 제공할 수 있습니다. |
| F 대화 공간과 지식 공간 분리  | 자유 대화·질문과 별도로 정리 글·위키를 제공합니다.                                          | 진행 중인 토론과 오래 유지할 자료의 수명 차이를 반영합니다.                                                  | 글 이동, 편집 책임, 원문과 정리본의 연결이 필요합니다. 작성 시부터 완성도를 강요하면 참여가 어려워질 수 있습니다. 처음부터 관리할 자료와 담당자가 있다면 작은 안내부터 제공할 수 있습니다.  |

B와 C는 같은 작성 기능을 공유할 수 있습니다. 필터는 목록을 좁히고, 이름 있는 게시판은 설명·대표 글·돌아올 위치를 통해 그곳의 활동을 알려줄 수 있습니다. 같은 기능을 쓰더라도 이러한 공간 구성이 도움이 되는지는 비교할 가치가 있습니다. GitHub의 General·Ideas·Show and tell도 같은 대화 형식을 쓰는 별도 카테고리입니다. 이는 기능 차이가 게시판 분리의 필수 조건은 아니라는 반례이며, 참여 효과가 입증되었다는 뜻은 아닙니다. [GitHub 공식 문서](https://docs.github.com/en/discussions/managing-discussions-for-your-community/managing-categories-for-discussions)

질문의 응답 구조, 공지의 작성 권한, 위키의 편집 이력처럼 동작 차이가 생기면 그에 맞는 기능도 구분해야 합니다. 데이터를 물리적으로 분리하는 것과 화면에 게시판을 보여주는 것은 별개의 결정입니다.

회원 수가 적다는 이유만으로 게시판을 금지하지 않습니다. 예상 회원 수로 글 발생량을 알 수 없고, 소수라도 별도 공간이 필요한 집단이 있을 수 있습니다. B는 도움을 줄 질문과 자료를 빠르게 찾게 할 수 있다는 가설입니다. A에서도 제목·검색·주제 정보로 같은 일을 충분히 할 수 있는지, C의 이름 있는 공간이 더 이해하기 쉬운지 함께 비교해야 합니다. 주제가 겹친다는 사실만으로 목적을 하나 선택하게 할 필요까지 증명되지는 않습니다.

## 잠정 추천안의 작성 기준

첫 선택은 ‘어떤 도움이나 반응을 원하나요?’로 설명합니다. 아래 명칭은 최종 문구가 아니라 비교할 후보입니다.

| 목적 후보 | 설명                                                     | 포함하는 글                                                           |
| --------- | -------------------------------------------------------- | --------------------------------------------------------------------- |
| 질문      | 막힌 부분에 대해 사람의 도움을 받습니다.                 | 오류·해석·도구 사용·학습 방향 질문, AI 결과를 함께 검토해 달라는 요청 |
| 공유      | 과정·설명·자료·결과물을 다른 사람이 활용하도록 올립니다. | 분석 기록, 튜토리얼, 도구 소개, 자료와 링크, 비교 실험, 실패 과정     |
| 자유      | 경험·의견·소식을 나누고 대화합니다.                      | AI 시대 공부의 가치, 진로, 연구 방향 토론, 근황, 모임 제안            |

‘공유’가 너무 넓게 느껴지면 ‘분석·자료’ 또는 ‘자료 공유’와 비교합니다. ‘분석’만 두면 튜토리얼·도구 소개·링크가 빠지는 문제가 있고, 별도 ‘자료’ 게시판을 추가하면 다시 경계가 늘어납니다. 전체 메뉴와 검색에서 이 명칭을 설명 없이 이해하는지 확인한 뒤 정합니다.

질문에 분석 내용이 포함되어도 도움 요청이 중심이면 질문으로 표시하는 방법을 비교할 수 있습니다. 질문이 나중에 해결되어도 원문의 성격을 자동으로 바꾸지는 않습니다. 별도의 정리 글이 필요하면 질문과 연결합니다. 공유 글의 끝에 질문 한 문장이 있다고 반드시 질문으로 바꾸지도 않습니다.

다만 주된 목적 하나를 고른다고 발견 문제가 해결되는 것은 아닙니다. 재사용할 분석 과정을 올리면서 핵심 부분의 검토를 부탁한 글은 질문과 공유 양쪽에서 찾을 필요가 있을 수 있습니다. 다음 예시의 분류는 유일한 정답이나 완전한 작업 목록이 아닙니다. 작성자가 고르는 데 망설이지 않는지와 독자가 필요한 글을 놓치지 않는지를 함께 확인합니다. 이를 해결하려고 첫 출시부터 복수 목적·도움 요청 상태·여러 필수 입력을 추가하지는 않습니다. 혼합 글을 억지로 쪼개거나 반복 게시하게 만들지 않습니다.

자유는 ‘나머지’나 ‘낮은 품질’이라는 뜻으로 사용하지 않습니다. 기술적 의견 교환과 긴 대화도 커뮤니티의 중요한 활동입니다. 카톡의 즉석 대화와 달리 웹에서 읽고 다시 이어 갈 가치가 있는 대화를 받을 수 있습니다.

## AI 활용 메뉴를 어떻게 해석할 것인가

현재 ‘AI 활용’은 질문·분석·자유와 같은 단일 유형 값입니다. 따라서 AI 작업법 질문을 질문으로 넣으면 AI 활용 목록에는 나타나지 않습니다. 반대로 AI 활용으로 넣으면 질문 목록에서 빠집니다. 이 충돌은 메뉴 명칭만 바꿔서는 해결되지 않습니다. [현재 구현 확인](sources.md)

| 선택            | 회원이 기대하는 것                                            | 제안                                                                                                    |
| --------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 주제 태그       | AI 관련 질문·분석·대화를 함께 찾습니다.                       | B의 시작점으로 적합하다는 판단입니다. AI가 글을 대신 써 주는 기능처럼 표현하지 않습니다.                |
| 주제별 모아보기 | AI 분석 작업법과 실패 사례를 바로 찾아 읽습니다.              | 중요 주제의 발견 경로를 강조하려면 E로 제공할 수 있습니다. 자동 목록과 운영자가 고른 자료를 구별합니다. |
| 전용 작업 공간  | 비교 실험, 재현 자료, 공동 워크플로 관리 등 별도 일을 합니다. | 실제로 제공할 기능과 유지할 사람이 정해지면 독립 공간을 검토합니다.                                     |

AI가 글의 맞춤법을 다듬었다는 이유만으로 AI 리버싱 주제로 넣지는 않는 기준을 제안합니다. 분석 방법이나 검증 대상에 AI가 중요한 경우를 모아야 목록의 의도가 분명해집니다. AI는 도구일 수도 있고 연구 주제나 방법일 수도 있습니다.

AI 분석 방법과 실패 사례를 함께 다루는 활동이 첫 방문자의 참여 이유라면, 첫 공개부터 짧은 안내와 실제 대표 글을 연결할 수 있습니다. 자동 모음이나 별도 실험 시스템이 완성될 때까지 발견 경로를 미룰 필요는 없습니다. 실제 읽을거리 없이 빈 메뉴나 장식용 소개 영역부터 늘리는 것은 피합니다.

별도의 상세 AI 검수 영역과 회원이 호출하는 AI 댓글은 게시판 분류와 독립적인 기능입니다. Jev 공개 전 최소검수도 내용의 사실성·학습 가치·법적 적합성을 보증하지 않습니다. 이미 결정한 공개 게이트는 어떤 분류를 선택해도 유지합니다.

## 첫 화면과 필터를 제안하는 방식

목적은 답할 질문을 찾고, 필요한 자료를 다시 쓰고, 진행 중인 대화에 참여하는 것입니다. 최신 활동뿐 아니라 무엇을 배울 수 있는 곳인지도 실제 콘텐츠로 보여줄 필요가 있습니다. 처음부터 모든 속성을 고르는 검색 화면을 메인으로 만들지 않습니다. NN/g는 필터가 사용자에게 중요한 속성과 맞아야 하고, 여러 속성으로 탐색하는 구조는 유지 부담도 크다고 설명합니다. 다음 화면 구성은 이를 우리 흐름에 적용한 가설입니다. [NN/g 설명](https://www.nngroup.com/articles/filters-vs-facets/)

1. **전체 목록을 기본 진입점으로 유지하는 안을 제안합니다.** 최신 글과 실제 정리 자료의 안내를 함께 제공할 수 있습니다. 무엇을 먼저 강조할지는 웹의 핵심 역할에 맞춰 비교합니다. ‘최근 활동’은 작성 시각순과 의미가 다르므로 별도 정렬로 검토합니다. 인기순을 기본으로 두는 가정은 하지 않습니다.
2. **빠른 목적 필터와 검색을 먼저 제공합니다.** B를 선택하면 전체·질문·공유·자유를 비교합니다. AI나 도구는 같은 자리에서 서로 배타적인 종류를 고르게 하지 않습니다.
3. **글의 태그를 누르면 그 태그에 정확히 해당하는 글을 찾습니다.** 현재 부분 문자열 검색을 정확한 태그 필터처럼 보이게 하지 않습니다. 태그 입력에는 기존 이름 제안을 먼저 제공하는 정도에서 시작합니다.
4. **선택한 조건은 화면에서 보이고 개별로 지울 수 있어야 합니다.** 예를 들어 ‘질문 / Ghidra / Windows’가 선택되었다면 그 조건의 결과라는 점을 명시합니다. 검색어만 지우기와 모든 조건 지우기를 구별합니다.
5. **여러 태그를 조합하는 기능은 후속 후보입니다.** 처음에는 검색과 정확히 일치하는 단일 주제 선택부터 검토합니다. 복수 조건을 제공하게 되면 ‘모두 포함’과 ‘하나 이상 포함’ 중 어떤 동작인지 명시하고, 말없이 바꾸지 않습니다.
6. **목록과 글 사이를 오가도 찾던 맥락을 유지합니다.** 필터·검색어·페이지와 돌아올 위치를 보존합니다. 탭을 바꾸거나 검색 결과를 갱신해 현재 스크롤 아래에 빈 공간만 남는 경우에는 결과 시작점이 보이도록 처리할 필요도 있습니다. 무조건 같은 픽셀을 유지하는 규칙만으로 판단하지 않습니다.
7. **빈 결과는 완화할 조건을 보여줍니다.** 비공개 글까지 세어 결과 수를 만들지 않습니다. 결과 수를 표시한다면 공개 글 기준의 총수인지 현재 페이지 수인지 구별합니다.

주제별 모아보기나 위키를 후속으로 제공할 때도 글마다 원래 주소와 댓글 흐름을 유지합니다. 같은 분석 글을 AI·Ghidra·게임 보안 경로에서 발견하게 할 수 있지만, 내용을 복사해서 서로 다른 댓글판을 만들지는 않는 방향을 제안합니다.

## 태그를 자유롭게 쓰되 정리 비용을 제한하는 방법

처음부터 운영체제·CPU·도구·분석 단계·난이도·방법을 각각 필수 입력으로 만들지 않습니다. 기존에 쓰이는 이름을 보여 주고 선택적으로 붙이는 정도부터 비교합니다. 태그 자동완성이나 관리 화면 전체가 첫 출시 조건은 아닙니다. 구체적인 기술 주제를 모르는 초보자도 질문을 쓸 수 있어야 합니다.

‘Ghidra/ghidra’, 한국어 표기와 영문 표기처럼 실제로 중복이 생기는 경우를 정리 대상으로 삼습니다. 동의어와 의미가 다른 말을 무리하게 합치지는 않습니다. 태그를 바꿀 때 원문의 내용이나 권한·검수 상태를 바꾸지 않으며, 기존 주소로 들어오는 경로도 고려합니다. 자동 태그 제안은 작성자의 확인을 받는 보조 수단으로 후속 검토할 수 있습니다.

주제를 찾아보는 태그, 사람의 도움 요청, 검수 결과가 모두 똑같은 자유 입력 칩으로 보이지 않게 합니다. ‘검증됨’, ‘허가받음’ 같은 문구를 작성자가 태그로 넣어도 실제 검증이나 권한 기록으로 인정하지 않습니다. 숙련도도 자동 평가나 사람 등급으로 만들지 않습니다.

## 검색 유입과 지식 축적

공개 글에는 직접 접근할 수 있어야 합니다. 정리한 주제 페이지가 유용할 수 있지만, 모든 필터 조합을 검색에 노출시키는 것으로 SEO·AEO·GEO를 해결할 수는 없습니다. Google은 필터 URL 조합이 크롤링 부담과 새 URL 발견 지연을 만들 수 있다고 설명합니다. [Google 공식 안내](https://developers.google.com/crawling/docs/faceted-navigation)

따라서 글의 고유 주소와 실제로 설명·자료가 갖춰진 주제 페이지를 중심으로 검색 유입을 준비하는 방향을 제안합니다. 일반 검색 결과와 임의의 필터 조합은 색인 필요를 따로 판단합니다. 구체적인 robots·canonical·noindex 처리는 구현 단계에서 검토하며, 여기서 하나의 방식으로 확정하지 않습니다. AI 검색 노출에 대한 보장이나 확인되지 않은 효과를 주장하지 않습니다.

‘공유 글’이라는 유형은 편집 완료·검증 완료를 의미하지 않습니다. 질문과 대화에서 얻은 정보를 포스트나 위키로 정리할 수 있고, 원문과 근거를 연결합니다. 편집자·검수 대상 버전·재검증 이력이 필요해질 때 지식 공간의 작업 방식을 갖춥니다. 원본 카톡을 검색 가능한 대화 아카이브로 제공하는 요구는 없습니다.

## 언제 게시판을 실제로 나눌 것인가

다음은 고정된 운영 규칙이 아니라 다음 분리를 검토할 관찰 기준입니다. 보편적인 회원 수나 일일 글 수 기준은 확인되지 않았으므로 임의의 임계치를 정하지 않습니다.

| 관찰되는 상황                                                   | 먼저 시도할 것                                         | 독립 공간을 검토할 이유                                                                       |
| --------------------------------------------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| 특정 주제를 원하는 회원이 계속 같은 조건을 선택합니다.          | 해당 주제의 바로가기나 팔로우를 검토합니다.            | 별도 독자·작성자 집단과 지속적인 운영 수요까지 생깁니다.                                      |
| 전체 목록에서 읽거나 답할 글을 찾기 어렵다는 의견이 반복됩니다. | 목적·주제 필터, 정렬, 관심 주제 표시를 조정합니다.     | 필터로 해결되지 않는 맥락·정체성·반복 방문의 이유가 있거나, 서로 다른 대화 규칙이 필요합니다. |
| 같은 글을 어디에 쓸지 반복해서 헷갈립니다.                      | 명칭·설명·예시를 수정하거나 목적 분류 자체를 줄입니다. | 분류를 더 늘리는 것이 해결이라는 가정을 하지 않습니다.                                        |
| 공동 편집 자료의 최신성과 검수 이력이 필요합니다.               | 원문에 정리 글을 연결하는 흐름부터 만듭니다.           | 위키의 편집·버전 관리가 일반 댓글과 달라집니다.                                               |
| 강의·실습·CTF 운영이 시작됩니다.                                | 일반 글로 설명할 부분과 운영 기능을 구별합니다.        | 진도·제출·채점·공개 시점이 필요한 별도 작업입니다.                                            |
| 운영 공지나 접근 제한 자료가 생깁니다.                          | 실제 권한과 공개 범위를 명시합니다.                    | 공개 태그 필터는 권한 경계를 대체할 수 없습니다.                                              |

초기 확인은 거대한 분석 대시보드보다 실제 사례를 보고 판단합니다. 글을 작성할 때 망설였던 위치, 원하는 자료를 찾지 못한 이유, 질문과 공유를 잘못 찾은 사례, 특정 주제에 답하거나 작성하는 사람이 실제로 따로 있는지를 기록합니다. 활동량이 부족한 기간의 비율을 근거로 분리를 확정하지 않습니다.

## 다음 단계에서 필요한 큰 결정

지금 선택할 것은 세부 태그 목록이나 게시판 수십 개가 아닙니다. **A처럼 분류 없이 시작할지, B처럼 목적별 필터를 둘지, C처럼 이름 있는 소수 게시판을 둘지**를 먼저 비교합니다. D는 분야별 공동 활동이 중심일 때의 대안입니다. E의 주제 진입점과 F의 정리 자료 안내는 A·B·C 어느 쪽과도 결합할 수 있으며, 반드시 B 이후여야 하는 것은 아닙니다.

제안은 **전체 목록과 서로 겹치는 주제의 발견 경로를 유지하고, 목적 필터는 A·C와 비교할 B 후보로 두는 방향**입니다. ‘질문·공유·자유’라는 이름이나 목적 하나만 선택하는 방식은 확정하지 않습니다. 실제 준비된 AI 자료나 정리 글이 있다면 초기부터 그 입구를 제공할 수 있습니다. 다음 구현에서는 선택한 구조로 작성과 찾기 흐름부터 완성하고, 상세 분류 체계는 실제 불편이 확인될 때 추가합니다.

첫 개선의 공통 후보는 **주제 하나로 공개 글 찾기 → 검색으로 좁히기 → 읽기 → 같은 목록으로 복귀**입니다. 게시판 구조를 정하기 전에도 비교할 수 있는 동작입니다. 여러 태그 조합, 주제 팔로우, 자동 분류, 개인화와 위키 시스템 전체는 이 개선의 선행 조건으로 삼지 않습니다. 이름 있는 공간을 선택해도 먼저 실제 글과 설명으로 작게 구성할 수 있습니다.

태그를 클릭할 때 기존 조건을 해제하고 전체 유형의 주제 목록으로 이동하는 방식과, 목록 안에서 조건을 추가하는 방식을 구별해야 합니다. 처음에는 전자를 글의 태그 링크에 적용하고, 그 목록에서 목적·검색을 추가해 좁히는 동작을 비교하는 안을 제안합니다. 복귀는 브라우저 뒤로가기뿐 아니라 화면의 목록 링크에서도 확인합니다. 현재 글 화면의 복귀 링크는 `/`로 가며 이전 조건을 전달하지 않습니다. 조건이 URL에 남는 것과 읽던 위치가 보존되는 것도 따로 확인합니다.

현재 검색은 전체 공개 글에서 일치 조건을 적용한 뒤 최신 최대 30개를 반환합니다. 최신 30개 안에서만 검색하는 구조는 아닙니다. 페이지 이동 전에는 화면의 개수를 전체 결과 수로 표시하지 않아야 합니다. 이후 태그 후보나 건수 기능을 넣더라도 보류·오류 글에만 있는 정보는 공개하지 않습니다.
