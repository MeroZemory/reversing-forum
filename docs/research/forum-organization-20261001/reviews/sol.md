## 남은 UX·데이터 보완

1. **작성 부담: 동의·보완.** 목적·주제·상태·형식·작업 공간의 구분은 내부 판단으로 유지하면 됩니다. 현재 폼은 자유가 기본값인 유형 하나와 선택 태그만 받습니다(`src/components/post-form.tsx:59`, `:91`). 서버는 태그 최대 5개·각 24자를 검사합니다(`src/server/forum.ts:173`). 초보자가 태그 없이 쓸 수 있게 유지하고, 혼합 글에 정확한 목적 선택·추가 상태·복수 목적을 필수로 요구하지 않습니다. 분류 예시를 이해하는지와 독자가 그 글을 놓치는지는 별도로 확인해야 합니다.

2. **태그와 검색: 보완.** 현재 글의 태그 링크는 `/?q=태그`이며 제목·본문·태그 JSON의 부분 문자열을 찾습니다(`src/app/posts/[id]/page.tsx:92`, `src/server/forum.ts:57`). 정확한 태그 필터라는 보고서의 설명은 제안이며 현 구현이 아닙니다. 첫 단계는 단일 태그의 정확한 일치로 제한합니다. 권고 동작은 ‘태그 링크 → 전체 유형의 해당 주제’로 이동하며 기존 목적·검색을 해제하는 것입니다. 이동 후 선택 태그를 표시하고, 그 목록에서 목적·검색을 추가하면 함께 적용합니다. 복수 태그를 지원할 때만 ‘모두 포함’과 ‘하나 이상 포함’을 명시합니다. 한 글에 여러 태그를 붙이는 기능과는 구별됩니다.

3. **조건·복귀·스크롤·빈 결과·수량: 보완.** 다음 차이가 구현 범위에 남아 있습니다.

| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

4. **이동·마이그레이션과 비공개 경계: 보완.** 유형은 DB의 필수 문자열이며 서버의 `postKinds` 검증을 받습니다. 태그는 JSON이고, 유형 값의 DB `CHECK` 제약은 없습니다(`src/server/db.ts:9`, `src/server/forum.ts:171`). 표시 이름 변경·기존 글 재분류·게시판 진입점 추가를 한 작업으로 묶지 않습니다. `workflow`를 목록에서 지우기만 하면 기존 글의 표시·필터 호환성이 흔들릴 수 있습니다. 이동 시 ID·댓글 연결·작성자·공개 상태를 보존해야 하며, Jev 입력에 유형·태그도 포함되므로 당시 검수 입력과 현재 정보가 달라지는 점을 확인해야 합니다.

   현재 공개 목록은 `published`만, 비공개 상세는 작성자만 허용합니다(`src/server/forum.ts:55`, `:92`). 새 건수·페이지 총수·태그 후보도 같은 공개 경계를 따라야 합니다. 타인의 보류 글에만 있는 태그를 후보로 보여주거나 ‘숨긴 글이 더 있다’고 알리면 내용 외의 정보도 누출됩니다. 작성자 본인의 비공개 글도 공개 목록 건수에 섞지 않습니다.

5. **댓글 0·미답변·해결·검증: 동의.** 수정된 출처 문서는 이 등치를 부정합니다. 실제 `commentCount`는 작성자 댓글과 답글도 포함한 행의 개수입니다(`src/server/forum.ts:34`). 유효 답변·해결·채택·검증의 기록이 아닙니다. ‘댓글 없음’을 ‘미해결’로, 보충 댓글 하나를 ‘답변 완료’로 표시하지 않습니다. Jev 공개 전 최소검수는 사실 검증이 아니며, 공유 유형이나 ‘검증됨’이라는 자유 태그도 검증 근거가 아닙니다. 답변 채택 정책은 이번 결정에 추가하지 않습니다.

6. **SEO URL과 근거: 동의·보완.** 필터 URL의 크롤링 부담을 설명하고 SEO·AEO·GEO 성과를 보장하지 않은 표현은 적절합니다. 고유 글 주소와 내용이 있는 주제 페이지를 우선하자는 부분은 프로젝트의 설계 판단입니다. 공유·뒤로가기용 조건 URL과 검색엔진 색인 여부는 별개 결정입니다. 확인한 공식 근거는 아래 두 건으로 한정합니다.

| ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## A·C를 우선할 조건과 첫 구현 한 단계

- **A 우선:** 목적 선택에서 초보자·혼합 글 작성자가 멈추지만, 독자는 제목·검색·주제로 필요한 질문과 자료를 충분히 찾는 경우입니다.
- **C 우선:** 이름·설명·대표 글·공동 활동의 위치가 있어야 참여할 곳과 돌아올 곳을 이해하는 경우입니다. 같은 폼을 사용하거나 글이 적다는 이유로 배제하지 않습니다. 전체 목록과 주제별 발견 경로를 함께 유지할 수 있습니다.
- **B 선택:** 목적 선택 부담이 작고 필터가 실제 찾기 작업을 돕는다는 관찰이 있을 때입니다. 회원 수 예상이나 사례 메뉴만으로 확인되지 않았습니다.

**가장 작은 첫 구현은 기존 유형의 재분류 없이 ‘태그 하나로 공개 글 찾기 → 검색으로 좁히기 → 읽기 → 같은 목록으로 복귀’를 완성하는 것입니다.** 기존 작성 폼과 Jev 공개 전 검수를 사용하고 위의 단일 태그·조건 해제·복귀·표시 한도만 연결합니다. A·B·C 어느 결론에서도 재사용할 수 있습니다.

유형 이름 교체와 일괄 이전, 복수 태그 필터·자동완성·팔로우·해결/검증 상태·위키·CTF는 완료 조건에서 제외합니다. 페이지 이동은 별도 TODO로 남기되, 30개를 넘는 결과에서 이전 자료에 접근할 필요가 확인되면 우선합니다. 실제 자료가 준비되어 있다면 짧은 안내와 대표 글 링크로 발견 경로를 제공할 수 있습니다.

## 수용 후 확인할 사용자 작업 5개

아래는 제안 수용 후의 과제이며, 이번 검수에서 새 동작이 통과했다는 뜻은 아닙니다.

1. **입문자가 분석 내용과 도움 요청을 함께 작성합니다.** 태그 없이 등록하고, 추가 상태나 형식을 입력하지 않습니다. A·B·C에서 분류를 망설인 지점과 독자의 발견 누락을 기록합니다.
2. **Ghidra 태그를 눌러 관련 글을 찾습니다.** 정확한 태그가 붙은 공개 글만 나오고 본문에만 있는 글은 제외됩니다. 서로 다른 유형의 관련 글을 함께 찾고, 목적·검색을 추가·개별 해제합니다.
3. **모바일에서 목록 아래의 글을 읽고 복귀합니다.** 브라우저 뒤로가기와 화면의 복귀 링크로 조건·위치를 되찾습니다. 결과가 적거나 없어도 안내가 보이고 키보드로 작업을 이어갑니다.
4. **일치 결과가 30개보다 많은 자료를 찾습니다.** 제목 검색으로 오래된 글에 도달하며 30개 표시를 전체 총수로 오해하지 않습니다. 빈 결과에서 개별·전체 조건 해제를 수행합니다. 후속 페이지 기능을 수용하면 두 번째 페이지와 조건 변경 후 첫 페이지 복귀도 확인합니다.
5. **작성자·다른 회원·비회원이 공개·보류·오류 글을 조회합니다.** 작성자는 내 글에서 비공개 글을 확인하지만 공개 검색·태그·건수·후보에는 공개 글만 나옵니다. 타인은 비공개 고유 주소로도 읽지 못하고, 댓글 수가 해결·검증 표시로 바뀌지 않습니다.

큰 결정 질문은 두 개면 충분합니다: 첫 방문에서 질문·대화와 자료 재사용 중 무엇을 먼저 성공시킬지, 그리고 실제 작성·찾기 작업에서 A·B·C 중 어떤 방식이 부담과 누락을 줄이는지입니다.

## 실제 확인 범위와 한계

직접 확인한 자료는 README·TODO, 보고서·출처의 초안과 수정본, 요청된 네 코드 파일, 필요한 목록·DB·글 상세 코드와 기존 테스트·설정입니다. Next.js Link·Form의 스크롤 의미는 설치된 버전의 로컬 공식 문서로 확인했습니다. 주요 현 구현 서술은 코드와 일치합니다.

앱을 수정하지 않고 실제 인증 파일·카톡 원문·기존 DB를 제외한 임시 복사본에서 다음 명령을 실행했습니다. 이미 실행 중이던 E2E의 종료 결과를 회수하여 오류 응답까지 통과한 것을 확인했습니다. 새 테스트를 추가로 시작하지 않았습니다.

| `npm.cmd run test:e2e -- --grep '목록 탭\|보류·API 오류'` | 헤드리스 테스트 3개가 통과했습니다. 목록 탐색 1개, 보류·오류 응답의 비공개 경계 각각 1개입니다. |

**임시 복사본의 총 테스트 통과 수는 16개(서버 13개 + E2E 3개)입니다.** E2E는 임시 실행기에서 `.env` 읽기를 제외하고 별도 포트·DB와 webpack 개발 서버를 사용했습니다. 이 결과는 기본 빌드 방식이나 실제 앱의 별도 검증을 대신하지 않습니다. 부모 작업이 보고한 브랜드 E2E 2개·서버 테스트 13개·기본 Next.js 빌드 통과는 독립 확인 결과에 합산하지 않습니다. 정확한 태그와 새 복귀 흐름 등 제안 기능의 완료·검증을 의미하지도 않습니다.

실제 회원의 작성 부담·활동량, 다른 포럼의 운영 성과, 미구현 정확한 태그·복수 조건·페이지·글 복귀 동작은 확인하지 않았습니다. 이후 추가로 수정된 판본도 이 기록의 확인 범위에 포함하지 않습니다. 이 작업에서 변경한 프로젝트 파일은 `reviews/sol.md` 하나입니다.
